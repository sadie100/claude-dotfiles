# cafe24-standard-notion-update

standard-cafe24 레포의 `mall/<몰>/setup.js` 현재 상태를 읽어, 사업부(비개발자)용 노션 운영 매뉴얼을 최신으로 맞추는 스킬.

- **대상 페이지**: 카페24 자사몰 표준안 운영 매뉴얼 — `https://app.notion.com/p/3c208b93608a8048976ce886b45c61fe` (page_id: `3c208b93608a8048976ce886b45c61fe`)
- **스키마 소스**: `mall/cloop/setup.js`와 `mall/itadmin001/setup.js` — 두 몰은 같은 스키마를 공유한다(몰별 예외 전역이 있을 수 있음. 예: 클룹 전용 `골라담기표기설정`). 값 예시는 실값에서 가져오되, 문서의 기준 예시는 클룹 값을 우선한다.
- **독자**: 비개발자 사업부. 문서 언어는 "화면 어디에 보이나 → 무엇을 적나"이고, 코드는 실제 들어가는 JS 오브젝트 형태 그대로 보여준다.

## 절차

### 1. 현재 스키마 추출과 문서 대조

```bash
grep -oE "^(var [가-힣A-Za-z0-9_]+|window\.[가-힣A-Za-z0-9_]+ =)" mall/cloop/setup.js mall/itadmin001/setup.js | sort -u
```

노션 페이지를 fetch(`notion-fetch`)해서 §3 섹션 목록·"개발팀이 관리하는 항목" 줄과 대조하고, 차이를 세 종류로 분류한다:

- **신규 전역** — 문서에 섹션이 없다
- **제거된 전역** — 문서에는 있는데 setup.js에서 사라졌다
- **스키마 변경** — 전역은 있는데 키 구성·의미·주석이 문서의 코드블럭과 다르다

차이가 없으면 "동기화 상태 일치"만 보고하고 끝낸다. 대조는 이름만이 아니라 **키 수준**까지 한다 — setup.js의 해당 전역 주석·키를 문서 코드블럭과 비교(파일 주석이 사실상 스키마 문서이므로 주석이 진실이다).

### 2. 변경 계획 결정

신규 전역마다 먼저 판단한다:

- **사업부 편집 대상인가?** 값이 화면 문구·이미지·링크·상품번호라면 §3 정식 섹션. 값이 인프라(API URL, 데이터 공급처 전환, 주문 데이터 규격)에 묶여 있으면 "개발팀이 관리하는 항목" 목록에 한 줄만 추가. 애매하면 사용자에게 물어본다.
- **어느 그룹에 넣나?** §3은 화면 순서 그룹이다: 공통(헤더·푸터·검색) → 메인페이지 → 상품상세 → 장바구니/마이페이지. 새 섹션은 해당 그룹의 흐름상 맞는 위치에 끼워 넣는다(맨 뒤에 몰아넣지 않는다).
- **관리자 화면과 미러인가?** 카페24 관리자 설정과 값이 짝을 이루면(예: 무료배송 기준액) §4 "양쪽을 함께 세팅해야 하는 것"에도 행/항목을 추가하고 섹션에 ⚠️ 경고를 단다.

제거된 전역은 섹션을 삭제한다. 스키마 변경은 코드블럭과 설명만 고친다(번호 변동 없음).

### 3. 섹션 작성 — 확립된 형식을 그대로 따른다

각 §3 섹션의 형식 (기존 섹션 하나를 fetch 결과에서 보고 톤을 맞출 것):

```markdown
### 3-N. <전역이름>
- **화면 어디에 보이나:** <페이지·영역을 비개발자 언어로>
（해당 영역 빨간 박스 스크린샷 — references/screenshot-capture.md 절차로 캡처·업로드）
- **무엇을 적나:** setup.js에서 `<전역이름>`을 찾아 수정합니다.
```javascript
// 키 설명은 이렇게 // 주석으로 — "비우면 어떻게 되는지"(fail-open 숨김)를 꼭 포함
var 전역이름 = { ... 실값 기반 예시, 긴 배열은 2~3항목으로 압축 ... };
```
- **주의사항:** <어긋나기 쉬운 지점 — 미러 관계, 스케줄 없음, 수동 갱신 필요 등>
```

작성 규칙:

- 예시값은 setup.js 실값에서 가져온다. 긴 이미지 URL은 `https://.../banner.png`로 축약하고 "웹FTP 업로드 후 나온 주소" 주석을 단다.
- setup.js 파일 주석에 있는 함정(값 형식, 디폴트 방향, 몰별 교체 필요)을 사업부 언어로 번역해 주의사항에 옮긴다.
- 값 스펙을 표로 만들지 않는다 — 코드블럭 + `//` 주석이 이 문서의 확정 형식이다.

### 4. 번호·상호참조 갱신 (중간 삽입 시)

섹션을 중간에 끼우면 뒷번호가 전부 밀린다. 문서 전체(§1 매핑표, §2, §4, §5 레시피)가 `§3-x`로 상호참조하므로:

1. **`§3-x` 참조를 replace_all로 일괄 치환하되 방향을 지킨다** — 번호가 **올라가는(삽입)** 경우는 내림차순(§3-20→§3-21 먼저, 마지막에 §3-5→§3-6), **내려가는(삭제)** 경우는 오름차순(§3-9→§3-8 먼저, 마지막에 §3-26→§3-25). 반대로 하면 방금 바꾼 토큰을 다음 op가 또 잡아 전부 한 번호로 뭉개진다(2026-09-01 실사고: 삭제에 내림차순을 써 §3-9~26 참조 30개가 모두 §3-8이 됨 — 원본 fetch 파일의 문맥 30자를 old_str로 삼아 하나씩 복구). `§` 접두 포함 토큰만 바꾸면 헤딩은 건드리지 않는다.
2. **헤딩(`### 3-x. 이름`)을 내림차순으로 개별 rename**.
3. 새 섹션 삽입 + §1 매핑표에 행 추가(해당 페이지 그룹의 표에, 화면 영역/보이는 것/세팅 위치 3열).

세 단계 모두 한 번의 `update-page(update_content)` 호출에 순서대로 담을 수 있다(배열은 순차 적용된다).

### 5. 노션 반영과 검증

- 편집 전 반드시 `notion-fetch`로 페이지의 **저장 형태**를 확인한다 — 표는 `<table header-row="true">` HTML로, 중첩 불릿은 탭 들여쓰기로, `~`·`>`·`{` 는 `\~` 식으로 이스케이프되어 저장된다. `old_str`은 fetch 결과에서 복사해야 매칭된다.
- **이미지 블록은 URL로는 매칭되지 않지만, 캡션으로는 매칭된다** — fetch가 내주는 이미지 URL은 요청마다 서명이 달라지는 S3 URL이라 `![캡션](URL)` 전체나 URL을 포함한 어떤 `old_str`도 `No matches found`가 난다(쿼리를 뗀 원본 URL, 앞줄 텍스트+`![캡션](` 조합도 실패, 2026-08-21 실측). 반면 **`![캡션]` 부분만을 `old_str`로 주면 매칭되어 캡션 수정이 된다**. 삭제·이동은 여전히 MCP로 불가능하다. 그래서 스크린샷을 지우거나 옮겨야 하면:
  1. 새 자리에는 재업로드로 넣는다(원본은 fetch 직후 서명 URL로 받아두면 됨 — [references/screenshot-capture.md](references/screenshot-capture.md) 5항).
  2. 옛 이미지는 이미지 앞뒤 텍스트만 `old_str`로 지우고(이미지는 고아로 남음), **캡션 앞에 `[제거 필요] ` 프리픽스를 붙여** 사용자가 UI에서 찾아 지울 수 있게 표시한다 — `old_str: "![캡션]"` → `new_str: "![[제거 필요] 캡션]"`. 저장 후 fetch에는 `![\[제거 필요\] 캡션]`처럼 대괄호가 이스케이프되어 나온다.
  3. 보고에 "고아 이미지 N장에 `[제거 필요]` 표시했으니 UI에서 삭제" 한 줄을 남긴다.
  - ⚠️ 캡션 프리픽스 op를 다른 op들과 한 `update_content` 호출에 섞으면 에러 없이 **조용히 미적용**될 수 있다(2026-09-01 실측: 24개 op 배치 안의 캡션 op만 누락, 같은 old_str을 단독 호출로 다시 보내니 적용). 캡션 편집은 단독 호출로 보내고 fetch로 확인한다.
  - ⚠️ 캡션이 같은 이미지가 여러 장이면(새로 넣은 사본과 옛 원본이 보통 같은 캡션이다) `old_str`이 **먼저 나오는 쪽 하나에만** 적용되고 에러 없이 성공한다(실측: 사용자가 고아를 먼저 지운 상태에서 정식 이미지에 프리픽스가 붙음). 그러니 프리픽스는 **옛 이미지를 지우기 전, 새 이미지를 넣기 전에** 먼저 붙이거나, 새 사본의 캡션을 옛것과 다르게 쓴다. 적용 후 fetch로 어느 이미지에 붙었는지 반드시 확인한다.
- 섹션 헤딩은 다른 곳(§2-1 등)에서 블록 앵커(`#<block_id>`)로 링크되어 있을 수 있다. 섹션을 옮기거나 번호를 바꿀 때 헤딩 블록을 지웠다 다시 만들면 앵커가 끊긴다 — **헤딩 rename은 그것만 담은 단독 `update_content` 호출**로 제자리 편집하고(블록 ID 보존됨, 실측), 섹션 이동은 헤딩이 아닌 쪽(본문)을 옮기는 방향으로 짠다. 편집 후 `notion-fetch(<block_id>)`로 헤딩 제목이 바뀌었는지 확인한다.
- 반영 후 결과를 사용자에게 보고: 추가/삭제/수정된 섹션, 번호 변동 범위, 남은 미결(스크린샷 미캡처 등).
- 스크린샷은 가능하면 같은 턴에 캡처해 채운다(절차: [references/screenshot-capture.md](references/screenshot-capture.md)). 데모몰에 해당 UI가 아직 없으면(설정이 비어 있어 fail-open 숨김) 📷 플레이스홀더로 두고 보고에 명시한다.

## 문서 구조 지도 (섹션을 찾을 때)

- **§0** 시작하기 전에 — setup.js 소개, 공통 규칙(fail-open, 웹FTP, 스케줄 없음, 캐시)
- **§1** 화면 ↔ 세팅 위치 매핑표 — 공통/메인/상품카드/상품상세/장바구니·마이 5개 표. **새 전역 추가 시 여기에도 행 추가**
- **§2** 카페24 관리자 세팅 (2-1~2-6) — setup.js와 무관하지만, 새 전역이 관리자 데이터와 폴백/미러 관계면 §2 항목과 상호참조를 건다
- **§3** setup.js 항목 (3-1~) — 이 스킬의 주 작업 영역. 마지막에 "개발팀이 관리하는 항목" 문단
- **§4** 양쪽 함께 세팅 — 관리자 ↔ setup.js 미러 항목
- **§5** 자주 하는 작업 레시피 — 새 전역이 기존 레시피(프로모션 오픈 등)에 끼어야 하면 단계 추가
