# cafe24-standard-notion-update

standard-cafe24 레포의 `mall/<몰>/setup.js` 현재 상태를 읽어, 사업부(비개발자)용 노션 운영 매뉴얼을 최신으로 맞추는 스킬.

- **대상 페이지**: 카페24 자사몰 표준안 운영 매뉴얼 — `https://app.notion.com/p/3c208b93608a8048976ce886b45c61fe` (page_id: `3c208b93608a8048976ce886b45c61fe`)
- **스키마 소스**: `mall/cloop/setup.js`와 `mall/itadmin001/setup.js` — 두 몰은 같은 스키마를 공유한다(몰별 예외 전역이 있을 수 있음. 예: 클룹 전용 `골라담기표기설정`). 값 예시는 실값에서 가져오되, 문서의 기준 예시는 클룹 값을 우선한다.
- **독자**: 비개발자 사업부. 문서 언어는 "화면 어디에 보이나 → 무엇을 적나"이고, 코드는 실제 들어가는 JS 오브젝트 형태 그대로 보여준다.
- **문서 구성**: 번호가 전혀 없다. H1 = 화면 영역, H2 = 화면 항목(제목 끝에 ` — setup.js` / ` — 관리자` / ` — 관리자 + setup.js` 접미사로 세팅 위치 표시). 색인은 노션 사이드 목차가 대신하므로 **별도의 화면↔위치 대응표를 다시 만들지 않는다.**

## 절차

### 1. 현재 스키마 추출과 문서 대조

```bash
grep -oE "^(var [가-힣A-Za-z0-9_]+|window\.[가-힣A-Za-z0-9_]+ =)" mall/cloop/setup.js mall/itadmin001/setup.js | sort -u
```

노션 페이지를 fetch(`notion-fetch`)해서 받은 마크다운에서 **코드블럭 안의 `^var ` / `^window.` 선언 이름**을 전부 뽑고(전역 ↔ 항목 매핑은 헤딩이 아니라 이 선언 줄과 그 위 `무엇을 적나` 줄로 판단한다 — 한 전역이 여러 항목에 흩어질 수도, 한 항목이 여러 전역을 담을 수도 있다), "개발팀이 관리하는 항목" 문단의 백틱 이름도 목록에 합쳐 대조한다. 차이를 세 종류로 분류한다:

- **신규 전역** — 문서 어디에도 선언이 없다
- **제거된 전역** — 문서에는 있는데 setup.js에서 사라졌다
- **스키마 변경** — 전역은 있는데 키 구성·의미·주석이 문서의 코드블럭과 다르다 (선언이 여러 코드블럭에 있으면 **전부** 고친다)

차이가 없으면 "동기화 상태 일치"만 보고하고 끝낸다. 대조는 이름만이 아니라 **키 수준**까지 한다 — setup.js의 해당 전역 주석·키를 문서 코드블럭과 비교(파일 주석이 사실상 스키마 문서이므로 주석이 진실이다).

### 2. 변경 계획 결정

신규 전역마다 먼저 판단한다:

- **사업부 편집 대상인가?** 값이 화면 문구·이미지·링크·상품번호라면 정식 항목. 값이 인프라(API URL, 데이터 공급처 전환, 주문 데이터 규격)에 묶여 있으면 "개발팀이 관리하는 항목" 문단에 한 줄만 추가. 애매하면 사용자에게 물어본다.
- **어디에 놓나?** 먼저 **영역(H1)** 을 고르고, 그 영역 안 H2들의 화면 순서상 맞는 위치를 정한다(맨 뒤에 몰아넣지 않는다).
  - 이미 그 화면 영역을 다루는 항목이 있으면 **새 H2를 만들지 말고 그 항목 안에** 넣는다 — `- **무엇을 적나:**` + 코드블럭을 하나 더 붙이거나, 방식이 갈리면 H3 소제목(`### … (setup.js)`)으로 나눈다. 세팅 위치 조합이 바뀌면 **헤딩 접미사도 함께 고친다**(예: `— 관리자` → `— 관리자 + setup.js`).
  - 해당하는 항목이 없으면 화면 영역 이름으로 새 H2를 만들고 접미사를 붙인다.
- **관리자 화면과 미러인가?** 카페24 관리자 설정과 값이 짝을 이루면(예: 무료배송 기준액) "양쪽을 함께 세팅해야 하는 것" 영역에도 항목을 추가하고 본문에 ⚠️ 경고를 단다.

제거된 전역은 항목(또는 그 항목 안 해당 블럭)을 삭제한다. 스키마 변경은 코드블럭과 설명만 고친다.

### 3. 항목 작성 — 확립된 형식을 그대로 따른다

기존 항목 하나를 fetch 결과에서 보고 톤을 맞출 것. setup.js 항목:

````markdown
## <화면 영역 이름> — setup.js
- **화면 어디에 보이나:** <페이지·영역을 비개발자 언어로>
（해당 영역 빨간 박스 스크린샷 — references/screenshot-capture.md 절차로 캡처·업로드）
- **무엇을 적나:** setup.js에서 `<전역이름>`을 찾아 수정합니다.
```javascript
// 키 설명은 이렇게 // 주석으로 — "비우면 어떻게 되는지"(fail-open 숨김)를 꼭 포함
var 전역이름 = { ... 실값 기반 예시, 긴 배열은 2~3항목으로 압축 ... };
```
- **주의사항:** <어긋나기 쉬운 지점 — 미러 관계, 스케줄 없음, 수동 갱신 필요 등>
````

관리자 항목은 `무엇을 적나` 대신 `- **관리자 어디서 세팅하나:** <관리자 메뉴 경로>` + `- **세팅 방법:** <무엇을 어떻게>` (필요하면 `- **동작 규칙:**`), 뒤는 동일하다. 두 방식이 섞이는 항목은 H3 소제목으로 `(관리자)` / `(setup.js)` 를 나눠 담는다.

작성 규칙:

- 예시값은 setup.js 실값에서 가져온다. 긴 이미지 URL은 `https://.../banner.png`로 축약하고 "웹FTP 업로드 후 나온 주소" 주석을 단다.
- setup.js 파일 주석에 있는 함정(값 형식, 디폴트 방향, 몰별 교체 필요)을 사업부 언어로 번역해 주의사항에 옮긴다.
- 값 스펙을 표로 만들지 않는다 — 코드블럭 + `//` 주석이 이 문서의 확정 형식이다.

### 4. 삽입 위치와 상호참조

번호가 없으므로 중간 삽입에 연쇄 갱신이 없다(예전 번호 체계는 일괄 치환 방향이 뒤집혀 참조 30개가 한 번호로 뭉개진 사고 이후 폐기했다 — 2026-09-01).

- **삽입**은 `update_content` op 하나면 된다: `old_str` = 바로 **다음 항목의 헤딩 줄**(또는 앞 항목의 마지막 줄), `new_str` = 새 항목 본문 + 그 줄. 헤딩 줄의 em dash와 앞뒤 공백(` — setup.js`)까지 fetch 결과에서 그대로 복사한다. 영역의 첫 항목으로 넣을 때도 앵커는 H1이 아니라 **현재 첫 H2 헤딩 줄**로 잡는다(H1 위로 밀려나지 않게).
- **상호참조는 평문**이다 — `"헤더 GNB 카테고리 메뉴" 항목`처럼 따옴표 안 헤딩 이름으로만 건다. 블록 앵커 링크를 쓰지 않는다.
- 헤딩 이름을 바꾸면 옛 이름을 따옴표째 grep해 찾아 `replace_all_matches`로 치환한다. 따옴표 붙은 토큰은 헤딩 줄과 절대 겹치지 않으므로, 아래의 단독 rename 호출 뒤에 안전하게 돌릴 수 있다.

### 5. 노션 반영과 검증

- 편집 전 반드시 `notion-fetch`로 페이지의 **저장 형태**를 확인한다 — 표는 `<table header-row="true">` HTML로, 콜아웃은 `<callout icon="…" color="…">` HTML(본문 탭 들여쓰기)로, 중첩 불릿은 탭 들여쓰기로, `~`·`>`·`{` 는 `\~` 식으로 이스케이프되어 저장된다. `old_str`은 fetch 결과에서 복사해야 매칭된다.
- **이미지 블록은 URL로는 매칭되지 않지만, 캡션으로는 매칭된다** — fetch가 내주는 이미지 URL은 요청마다 서명이 달라지는 S3 URL이라 `![캡션](URL)` 전체나 URL을 포함한 어떤 `old_str`도 `No matches found`가 난다(쿼리를 뗀 원본 URL, 앞줄 텍스트+`![캡션](` 조합도 실패, 2026-08-21 실측). 반면 **`![캡션]` 부분만을 `old_str`로 주면 매칭되어 캡션 수정이 된다**. 삭제·이동은 여전히 MCP로 불가능하다. 그래서 스크린샷을 지우거나 옮겨야 하면:
  1. 새 자리에는 재업로드로 넣는다(원본은 fetch 직후 서명 URL로 받아두면 됨 — [references/screenshot-capture.md](references/screenshot-capture.md) 5항).
  2. 옛 이미지는 이미지 앞뒤 텍스트만 `old_str`로 지우고(이미지는 고아로 남음), **캡션 앞에 `[제거 필요] ` 프리픽스를 붙여** 사용자가 UI에서 찾아 지울 수 있게 표시한다 — `old_str: "![캡션]"` → `new_str: "![[제거 필요] 캡션]"`. 저장 후 fetch에는 `![\[제거 필요\] 캡션]`처럼 대괄호가 이스케이프되어 나온다.
  3. 보고에 "고아 이미지 N장에 `[제거 필요]` 표시했으니 UI에서 삭제" 한 줄을 남긴다.
  - ⚠️ 캡션 프리픽스 op를 다른 op들과 한 `update_content` 호출에 섞으면 에러 없이 **조용히 미적용**될 수 있다(2026-09-01 실측: op 배치 안의 캡션 op만 누락, 같은 old_str을 단독 호출로 다시 보내니 적용). 캡션 편집은 단독 호출로 보내고 fetch로 확인한다.
  - ⚠️ 캡션이 같은 이미지가 여러 장이면(새로 넣은 사본과 옛 원본이 보통 같은 캡션이다) `old_str`이 **먼저 나오는 쪽 하나에만** 적용되고 에러 없이 성공한다(실측: 사용자가 고아를 먼저 지운 상태에서 정식 이미지에 프리픽스가 붙음). 그러니 프리픽스는 **옛 이미지를 지우기 전, 새 이미지를 넣기 전에** 먼저 붙이거나, 새 사본의 캡션을 옛것과 다르게 쓴다. 적용 후 fetch로 어느 이미지에 붙었는지 반드시 확인한다.
- **헤딩 rename은 그것만 담은 단독 `update_content` 호출**로 제자리 편집한다 — 헤딩 블록을 지웠다 다시 만들면 블록 ID가 바뀐다(제자리 편집은 ID 보존됨, 실측). 편집 후 `notion-fetch(<block_id>)`로 제목이 바뀌었는지 확인한다. 현재 문서의 상호참조는 전부 평문이라 앵커 파손 위험은 없지만, ID 보존은 계속 지킨다.
- **문서 전체 개편은 `replace_content` 한 방으로 가능하다**(2026-09-03 실측). 절차: 개편 전 페이지 **복제본을 만들어 두고** → 새로 `notion-fetch` → **그 즉시** 응답의 서명 URL로 이미지를 전부 내려받고(몇 분이면 403) → 이미지마다 `notion-create-file-upload` + curl로 재업로드해 `file-upload://<id>`를 얻어 새 본문에 끼운 뒤 → `replace_content` 한 번으로 본문을 갈아 끼운다. 블록 ID(앵커)는 살아남지 않으므로 상호참조는 평문만 쓴다.
- 반영 후 결과를 사용자에게 보고: 추가/삭제/수정된 항목 이름, 바뀐 헤딩과 그에 따른 상호참조 치환, 남은 미결(스크린샷 미캡처 등).
- 스크린샷은 가능하면 같은 턴에 캡처해 채운다(절차: [references/screenshot-capture.md](references/screenshot-capture.md)). 데모몰에 해당 UI가 아직 없으면(설정이 비어 있어 fail-open 숨김) 📷 플레이스홀더로 두고 보고에 명시한다.

## 문서 구조 지도 (H1 영역 순서)

- **시작하기 전에** — setup.js 소개, 공통 규칙(fail-open, 웹FTP, 스케줄 없음, 캐시), "스킨 최초 적용 시 켜둘 설정" 표(관리자 경로 / 값 / 꺼져 있으면 생기는 증상)
- **공통 — 헤더 · 푸터 · 검색** / **메인페이지** / **상품카드 (메인 · 목록 공통)** / **상품상세** / **장바구니 / 마이페이지** — 화면 항목 H2들이 사는 본체. 이 스킬의 주 작업 영역
- **개발팀이 관리하는 항목 (사업부는 만지지 않음)** — 인프라에 묶인 전역을 백틱 이름으로 나열한 문단
- **양쪽을 함께 세팅해야 하는 것 (⚠️ 놓치기 쉬움)** — 관리자 ↔ setup.js 미러 항목
- **자주 하는 작업 레시피** — 항목을 따옴표 이름으로 참조하는 단계 목록. 새 전역이 기존 레시피(프로모션 오픈 등)에 끼어야 하면 단계 추가
