# cafe24-standard-update-notice

표준안에 들어간 변경을 사업부(비개발자)가 읽을 슬랙 "[업데이트 안내]" 메시지로 옮기는 스킬. 결과물은 **문서 파일 하나**이고, 슬랙에 올리는 일은 사용자가 직접 한다. 그래서 사용자가 복사해서 그대로 붙일 수 있도록 슬랙 mrkdwn 문법으로 쓰고, 멘션할 사람만 자리 표시로 남긴다.

## 왜 이 형식인가

개발자끼리는 커밋 메시지로 충분하지만, 사업부는 "내 화면의 어디가 어떻게 달라졌고, 내가 뭘 해야 하는지"만 알면 된다. 그래서 메시지는 항상 세 질문에 답한다.

1. 무엇이 바뀌었나 (한 줄)
2. 어떻게 바뀌었나 — 항목마다 **기존 → 변경**을 짝으로
3. 어디서 확인하고, 뭘 만지려면 어느 문서를 보나

이 구조는 기존 공지(`references/example-slack.md`)에서 그대로 가져온 것이다. 새 형식을 발명하지 말고 그 예시의 톤과 번호 체계를 따른다.

## 입력을 모으는 순서

사용자가 준 것부터 쓴다. 부족한 건 아래 순서로 채우고, 그래도 모르면 한 번에 묶어서 물어본다.

1. **대화 맥락** — 같은 세션에서 작업을 막 끝냈으면 그 내용이 곧 입력이다. 다시 조사하지 않는다.
2. **PR 번호나 커밋 범위** — `gh pr view <n> --json title,body,commits`, `git log --format='%s%n%b' <range>`로 읽는다. 커밋 본문의 "배경 / 요구사항 / 구현 방식"이 사업부 언어로 옮길 재료다.
3. **반영 페이지 URL** — 변경이 보이는 운영몰 페이지. 운영 도메인(`https://<몰>.cafe24.com/...`)으로 적고, 아직 배포 전이면 URL 뒤에 "(배포 후 확인 가능)"을 단다. 개발 스킨 URL(`skin-skinN`)은 절대 넣지 않는다 — 사업부가 그 주소로 들어가면 안 된다.
4. **가이드 문서** — setup.js 설정이 생기거나 바뀐 변경이면 노션 운영 매뉴얼(`https://app.notion.com/p/3c208b93608a8048976ce886b45c61fe`)의 해당 항목 제목을 따옴표로 적어 링크한다. 항목 제목은 매뉴얼을 fetch해서 실제 헤딩 문자열을 복사한다(추측으로 적지 않는다). 매뉴얼에 아직 항목이 없으면 초안에 "📌 매뉴얼 항목 미작성"을 남기고 보고에서 `cafe24-standard-notion-update`를 먼저 돌리라고 알린다.

## 무엇을 빼고 무엇을 남기나

사업부가 행동하거나 알아둘 것만 남긴다. 판단 기준은 "이 줄을 읽고 사업부가 할 일이나 알아둘 것이 생기나"다.

- **남긴다**: 화면에서 보이는 변화, 사업부가 setup.js·관리자에서 직접 만질 값, 기간·조건 같은 동작 규칙, 요청자가 있었다면 그 요청이 반영됐다는 사실.
- **뺀다**: 내부 리팩터링, 파일 경로, 함수 이름, 테스트 수, 검사기 제거 같은 개발 인프라 변경, 실측 축(PC/MO·UA) 기록. 이런 건 PR에 있다. 한 PR에 개발용 변경만 있는 갈래가 섞여 있으면 그 갈래는 통째로 뺀다.
- **기술어 번역**: "fail-closed" → "조건을 하나라도 못 채우면 아예 안 보입니다", "lazy read" → 언급 자체를 하지 않음, "product_additional 모듈" → "상세정보 탭". 확신이 없으면 화면에서 보이는 결과로 바꿔 말한다.

## 출력 형식

파일은 `/tmp/update-notice-<짧은-영문-슬러그>.md` 에 쓰고, 답변에도 전문을 코드 블록으로 붙인다(사용자가 바로 복사하도록). 파일 안은 슬랙에 붙일 두 덩어리로 나눈다 — **본문 메시지**와 **스레드 답글**. 예시 공지가 제목만 본문에 올리고 내용은 스레드에 단 방식이라 그대로 따른다.

````markdown
## 본문 (채널에 올릴 메시지)

*[업데이트 안내] <화면 영역 + 무엇이 바뀌었는지 한 줄>* @<담당자1> @<담당자2>

## 스레드 답글

안녕하세요! 자사몰 표준안의 <영역>이 업데이트되어 공유드립니다.

1. 업데이트 내용
    ◦ <한 줄 요약 — 제목과 같아도 됨>
2. 업데이트 세부 내용
    ◦ *<항목 1>*
        ▪︎ 기존: <전에는 어땠는지>
        ▪︎ 변경: <이제 어떻게 되는지>
    ◦ *<항목 2>*
        ▪︎ 기존: …
        ▪︎ 변경: …
3. 반영 페이지
    ◦ <https://<몰>.cafe24.com/...|페이지 이름>
4. 설정 방법 (가이드 문서)
    ◦ <https://app.notion.com/p/3c208b93608a8048976ce886b45c61fe|자사몰 표준안 운영 매뉴얼> 의 "<항목 제목>" 항목을 참고해 주세요.

피드백 사항 있으실 경우 말씀 부탁드립니다!
감사합니다.
````

형식 규칙:

- 슬랙 mrkdwn이다. 굵게는 `*별표 하나*`, 링크는 `<URL|표시 텍스트>`. 마크다운 `**`·`[text](url)`은 슬랙에서 깨진다. 헤딩(`#`)도 쓰지 않는다 — 파일 안의 `## 본문`·`## 스레드 답글` 두 줄만 구분용이고 슬랙에 붙이지 않는다.
- 들여쓰기 글머리는 예시처럼 `◦`와 `▪︎`를 쓴다. 슬랙에서 목록을 붙여넣으면 이 모양이 유지된다.
- 4번(가이드 문서)은 setup.js·관리자 설정이 얽힌 변경에만 넣는다. 순수 UI 개선이면 3번까지만.
- 멘션은 `@<담당자>` 자리 표시로 둔다. 누구를 부를지는 사용자가 안다. 요청 스레드가 있어 요청자를 아는 경우에만 그 이름을 후보로 적고 "요청자"라고 표시한다.
- "기존/변경" 짝은 항목마다 반드시 둘 다 쓴다. 새로 생긴 기능이라 기존이 없으면 "기존: 없음(수동으로 상세설명에 넣어야 했음)"처럼 이전에 어떻게 하던 일이었는지를 적는다.
- 기간·조건이 있는 기능은 그 규칙을 사업부 언어로 한 줄 넣는다(예: "적어 둔 기간이 되면 자동으로 켜지고 끝나면 자동으로 사라집니다").

## 문장

독자가 사업부이므로 `ko-doc` 스킬의 규칙을 따른다 — 문장마다 서술어가 있고, 화살표·가운뎃점 나열·괄호 문장으로 잇지 않는다. 슬랙이라 존댓말 구어체("~됩니다", "~해 주세요")로 쓰되, 이모지는 예시 수준(없거나 한두 개)으로 절제한다. 초안을 쓴 뒤 한 번 읽고 개발 용어가 남았는지 확인한다.

## 보고

파일 경로와 전문을 보여주고, 아래를 한 줄씩 알린다.

- 자리 표시로 남긴 것(멘션, 미배포 URL, 매뉴얼 미작성 항목)
- 초안에서 일부러 뺀 갈래(개발 인프라 변경 등)가 있으면 그 이유
- 배포 전이면 "배포 후에 올려야 한다"는 점

슬랙에 보내는 도구는 호출하지 않는다. 사용자가 "보내줘"라고 명시해도 이 스킬의 범위 밖이니 초안을 넘기고 전송은 사용자에게 맡긴다.
